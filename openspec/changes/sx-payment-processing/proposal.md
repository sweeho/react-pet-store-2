# Payment Processing - Specification Proposal

## Summary

This specification extracts the payment processing capability from the legacy Java Pet Store application. The system captures and persists credit card information via CreditCardEJB entity beans, creating cards as part of purchase orders and cascade-deleting them when orders are removed. The design enforces transactional access and provides expiry date parsing with fallback defaults.

## Problem Statement

The legacy payment processing system stores credit card information in CMP entity beans integrated with order placement. The contracts governing entity creation, relationship management, data access, and expiry date parsing are implicit in the EJB configuration and implementation code. This specification captures the payment processing contracts so the capability can be rebuilt with explicit behavior and verifiable contracts.

## Solution Overview

Payment processing consists of:

- **CreditCard Entity (CMP 2.x)**: Persists cardNumber, cardType, expiryDate as strings
- **Three Creation Methods**: No-arg, full parameters, or value object
- **Expiry Date Parsing**: Extracts month/year from MM/YYYY format with legacy defaults
- **Data Retrieval**: getData() method returns CreditCard value object
- **PurchaseOrder Integration**: One-to-one container-managed relationship with cascade-delete
- **Accessor Methods**: Transactional getters/setters for all three fields
- **Credit Card Form**: HTML form for manual card entry (customer creation page)

## Key Behavioral Requirements

### Entity Persistence

CreditCard is a CMP 2.x entity persisting three string fields:

- cardNumber: Card number (accepts up to 30 characters)
- cardType: Card type (Java Card, Duke Express, Meow Card, etc.)
- expiryDate: Expiry in MM/YYYY format (slash-separated)

### Creation

Three creation paths supported:

1. **No-arg create()**: Creates empty card
2. **Parameterized create(cardNumber, cardType, expiryDate)**: Full card data
3. **Value object create(CreditCard)**: From CreditCard value object

### Expiry Date Handling

**Parsing:**

- getExpiryMonth(): Extracts text before "/" or defaults to "01"
- getExpiryYear(): Extracts text after "/" or defaults to "2010"

**Default values:** "01" (January) and "2010" (legacy default; likely outdated)

### Data Access

- getData() returns CreditCard value object with all three fields copied
- Accessor methods (getters/setters) provide individual field access
- All operations within Required transactions

### PurchaseOrder Association

- One-to-one container-managed relationship
- Created during PurchaseOrderEJB.ejbPostCreate()
- Cascade-deleted when PurchaseOrder is removed
- Unidirectional: navigable only from PurchaseOrder to CreditCard

### Access Control

- All methods: <unchecked/> permission
- No role-based authorization
- Available to any caller

### User Interface

Credit card input form includes:

- cardNumber text input (maxlength 30)
- cardType dropdown (3 options)
- expiryDate: separate month (01-12) and year dropdowns

## Implementation Scope

Includes:

- ✓ CreditCard CMP entity with three fields
- ✓ Three creation methods
- ✓ Expiry date parsing with fallback defaults
- ✓ Data retrieval via getData()
- ✓ Accessor methods (getters/setters)
- ✓ PurchaseOrder-CreditCard one-to-one relationship
- ✓ Cascade-delete semantics
- ✓ Transaction management (Required attribute)
- ✓ Access control (unchecked permission)
- ✓ Credit card input form

Excludes:

- Card number validation (Luhn algorithm, format)
- Card type enumeration enforcement
- Expiry date format validation
- Card holder name field
- Billing address verification
- Payment gateway integration
- Tokenization or encryption
- PCI compliance measures

## Implementation Considerations

### Entity Persistence

CreditCard uses EJB 2.x container-managed persistence. Primary key is auto-generated by container (primkey-field declared as java.lang.Object). All fields are strings; no type conversion or validation at the EJB layer.

### Expiry Date Defaults

The expiryYear default of "2010" appears to be legacy code from when the application was written. Production use of this default is unclear and likely incorrect for current dates.

### No Validation

No card number validation (length, Luhn), card type enumeration, or expiry date format validation is documented. Validation may occur at a different layer or may be missing entirely.

### Form Constraints

The customer creation JSP constrains year dropdown to 2001-2004, suggesting the form was not updated when the application aged. Current implementations would need to extend this range.

### Cascade Deletion

Removal of a PurchaseOrder automatically deletes the associated CreditCard via cascade-delete relationship. No separate cleanup is needed.

## Success Criteria

Implementation is successful when:

1. CreditCard entity persists cardNumber, cardType, and expiryDate as strings
2. Three creation methods supported (no-arg, parameterized, value object)
3. getExpiryMonth() returns month from expiryDate or defaults to "01"
4. getExpiryYear() returns year from expiryDate or defaults to "2010"
5. getData() returns CreditCard value object with all three fields
6. Accessor methods (getters/setters) work for all fields
7. All operations execute within Required transaction context
8. PurchaseOrder has one-to-one relationship to CreditCard
9. Cascade-delete removes CreditCard when PurchaseOrder is deleted
10. All methods accessible without role-based authorization
11. Credit card form displays with text input, dropdown, and date selects
12. All acceptance criteria scenarios pass without behavioral regression

## Assumptions and Constraints

- Card number accepted as string, no validation
- Expiry date format: MM/YYYY (slash-separated)
- Default expiry year "2010" is intentional (though likely outdated)
- No encryption or tokenization at this layer
- No cardholder name or billing address
- Card type is free-form string (not strictly enumerated at EJB level)
- Primary key auto-generated; natural key unspecified
- No audit trail or change history

## Open Questions for Business Clarification

1. Should the expiry year default be updated to current year or a configurable value?
2. Should card number validation be added (Luhn algorithm, length restrictions)?
3. Should card type be strictly enumerated at the EJB layer?
4. Should expiry date format validation be enforced?
5. Should the form year dropdown be updated to a current range (e.g., 2024-2034)?
6. Is PCI compliance required, and should card data be encrypted?
7. Should card holder name or billing address be captured?
